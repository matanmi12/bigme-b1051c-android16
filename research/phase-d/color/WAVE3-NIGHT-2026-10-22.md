Yesterday's numbers (Regal 21–23, Fast 128–131 per round) swiped a different pane and are not comparable. A true A/B
was run at 05:4x (module swap, 2 reboots, same bench): **0.1.30** Regal 56/37 updates, CPU 12.8/8.6 s; Fast 329/343
updates, CPU 23.0/23.8 s, gap 40–42 ms. **0.1.34** Regal 49/50, CPU 11.7/12.5 s; Fast 301/285, CPU 20.4/19.4 s, gap
42–43 ms. Per panel update the CPU is the same (~68 ms); 0.1.34 does ~12 % fewer Fast updates per round with ~15 % less
composer CPU. The gains are correctness (fenced reads) and small changes (a clock tick = 43 rows instead of 1860), not
raw scroll throughput; the full-screen read per frame is what still costs (see the dirty-rects idea).

Where the pass time goes now: the uncached read of the whole client target plus the dma-buf cache syncs (fixed cost),
not the conversion. Next step if it matters: read the vendor's own dirty rects (CommitInfo+0x20.., B1051C build,
HWC-COMMIT-POLICY.md §6) so static rows are not even read.

## 2. Wave 3 step 4 stages: in the shim as knobs, all off (0 = output unchanged)

`setprop vendor.debug.hwc.shim.<knob> <value>` as root, then a full refresh (`gc16_req`) or the next frame:

| Knob | Range | Stage | Note |
|---|---|---|---|
| `level_black` | 0..128 | input black point (8-bit), per channel | "text darkening" (13) |
| `level_white` | 0..128 | 255 − input white point, per channel | "background bleach" (13); 1D (cheap) |
| `ok_sat` | −100..300 | chroma change in OKLCh, % | 3D; greys protected below `ok_neutral` |
| `ok_neutral` | 0..100 | chroma/1000 under which saturation is scaled by (C/n)² | default 20 |
| `tone` | −100..100 | contrast around mid-grey on OKLab lightness, % | 3D; pushes whites/blacks out |
| `lut` | −1/0/1 | Bigme's stock 3D LUT: as stock (with vivid only) / never / always | |
| `vivid_fast` | 0/1 | keep the 3D stages in Fast/Extreme/A2 | default 0 |

Order inside the pipeline: levels → stock contrast/brightness curves → stock HSL vivid → OKLCh chroma + tone → stock
LUT. All of it is baked into the 64³ table (or the 256-entry curve when no 3D stage is on), so the per-frame cost does
not change with the knobs. E-Ink Control does not expose them yet: the per-app engine and a QS tile come after the A/B
settles the ranges.

## 3. Findings for the research item (wave 3 step 3)

- **"HD 256" is not a kernel dither.** `research/phase-d/stock-bigme-display-stack.md` line 109: on stock, mode 177 with
  dither flag 4 (the top bits of `global_refresh_mode`, = 0x800000B1) makes the vendor HWC run
  `xrz::EffectHandler::imageSmoothing` on the frame (libimage_process.so) and commit **dither 0**. Since Phase C the shim
  commits the client target (or now its own processed buffer) instead of the vendor's processed buffer, so the smoothing
  has never reached the panel on the GSI: HD 256 = plain 177, as the baseline session showed (S3 = S4). The owner's
  "177 with dither 0 looked sharp and clean" is the same thing. Options for wave 3: leave it (sharp), or add an own
  smoothing stage (a light blur/anti-alias that hides the CFA moiré the way stock HD 256 does), as a knob.
- **Fast dither 3 / 6:** the kernel line shows dither 3 with colour restoration off and 6 with it on (the stock note at
  line 136 says the opposite; the live observation wins).
- `/sys/kernel/debug/eink_debug/global_dither` (written 4 at runtime, then 0 again): the kernel line shows
  `dither=0(def=4)`, i.e. only the default changed, the per-update value the HWC passes is what counts. Nothing to gain
  there for HD 256.
