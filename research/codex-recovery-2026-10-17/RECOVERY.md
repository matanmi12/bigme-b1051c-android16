# B1051C recovery — 2026-10-17

## Outcome

The owner confirmed that **Android's initial setup screen appeared** after short presses of the power button during boot. USB debugging is not available following the earlier reset; no ADB `sys.boot_completed` verification was possible. Do not reboot solely to test this result.

Working procedure: power on for 3–5 seconds, release; when the display flashes, briefly press power about once per second for approximately 10 seconds, then stop and allow Android to start. This bypasses the hidden dm-verity corruption acknowledgement. It may be needed again on future boots. No permanent warning-state repair was applied.

## Evidence and diagnosis

* mtkclient caught the preloader, disabled the watchdog and successfully read the GPT and partitions. Device was held in DA while diagnosing.
* Captured `misc.bin`: normal BCB, slot B priority 15, tries 7, successful 1, correct CRC; slot A unbootable. **Never activate A.**
* Captured boot_b and vbmeta_b / vbmeta_system_b / vbmeta_vendor_b match their original backups byte-for-byte. The current boot is the official stock B image, SHA256 dd26e52466aedf7d93546b07741673af1ecac1d1b441f251e81d6878c00405e0.
* Earlier Claude full-super read/verification is retained in research/superchk and its task output: it matched the backup and the slot B AVB hashtrees. A full-device rewrite was unnecessary for this recovery.
* Current expdb records `androidboot.veritymode=eio`, successful AVB return, and `check_ota_result = 0`, followed by `mt_power_off new` approximately **5.04 seconds later**. That is an intentional power-off path, not evidence of a kernel crash or an e-ink PMIC latch.
* Offline disassembly of the unmodified backed-up LK (code starts at file offset 0x200, link address 0x48200000) identified the warning routine at 0x48262984. It draws the dm-verity corruption message, polls the power key 50 times at 100 ms, and calls power-off at 0x48262a14 if the key is not pressed. It returns to the boot path when the key is pressed. See `lk-xrefs.txt`, generated by `lk_xrefs.py`.
* The warning text is not visibly displayed to the owner on the e-ink screen. Pressing the key through that interval allowed Android to reach initial setup. This supports the hidden warning as the immediate boot blocker. The original cause of the failed Android 16 DSU boot remains unproven.
* The earlier explanation that `start save pllk log` proves a jump into Linux is incorrect: the string also occurs in the **power-off** path. Truncated display logs are not sufficient to diagnose a display hardware hang.

## What was changed in this session

With explicit approval, wrote a copy of the captured misc with `bootonce-bootloader` in its first 32-byte field (19 changed bytes; boot control unchanged). Readback matched exactly. LK did not consume this command and fastboot did not appear. Its binary contains `boot-fastboot` and `boot-recovery`, but no `bootonce-bootloader` string; do not assume generic BCB bootloader commands work here.

Using the same explicit rollback approval, restored **the exact captured original misc**, with exact readback verification (`misc-restored.bin`). No boot, vbmeta, metadata, userdata, seccfg, preloader, LK or calibration partition was written by Codex. The successful boot followed this restoration and the power-button acknowledgement.

## Earlier wipe details

At capture time metadata was all zero (39,780,352 bytes), not a formatted ext4 filesystem. The first 2 MiB of userdata were zero; bytes after that matched the pattern from Claude's earlier post-wipe read. The local mtkclient `da_es` implementation incorrectly treats a successful `writeflash` return as a failure, breaking after its first 2 MiB chunk. Therefore the earlier requested 256 MiB erase did not complete. This does **not** establish that an incomplete wipe was the boot blocker; the button-only recovery points to the warning instead.

Settings/app-data and KOReader backups remain in `settings-backup-2026-10-17`. Do not restore account/encryption/system databases blindly, and do not claim media files were backed up. No user-data restoration was performed in this session.
