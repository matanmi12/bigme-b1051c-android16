# microSD card not recognised — diagnosis 2026-10-18

Owner report: 128 GB card, FAT32, "no ROM recognises it". The system image is irrelevant: stock Bigme,
TrebleDroid GSI and every other ROM on this device run the **same kernel + device tree** (boot_b), and the
failure is entirely inside the kernel's SD host driver (mtk-sd / msdc1).

## What actually happens (evidence: `kmsg-sd-extract-2026-10-18.txt`, full log `kmsg-sd-full-2026-10-18.log.gz`)

1. The card is detected and initialised correctly every time:
   `mmc0: new ultra high speed SDR104 SDXC card at address b368`, `mmcblk0: mmc0:b368 SDABC 116 GiB`, MBR, one
   partition (type 0x0c) starting at sector 2048, vfat label `128 GB`, UUID `1D02-1A5A`.
   Host runs it at **SDR104 timing, 96 MHz actual** (`max-frequency = 100000000` in the DT; msdc source 192 MHz / 2).
2. vold mounts it, then the **first write** (creating `LOST.DIR`, or the vfat dirty bit) fails:
   `Unable to create LOST.DIR: I/O error`.
3. Kernel side: the write returns **data CRC errors** (`msdc_irq: events=0000A040` = DATCRCERR), the core
   requests a retune, MediaTek's `msdc_detect_bad_sd` counts the retunes (`bad_sd_detecter:1 … 10`) and at 10
   calls `msdc_set_bad_card_and_remove` → `block_bad_card=1`, card removed (`mmc0: card b368 removed`),
   vold reports `bad_removal`. The whole storm takes ~16 ms after the first write.
4. `block_bad_card=1` means the driver ignores the card until a **card-detect edge** (physical re-insert)
   or a driver re-probe. No CD interrupt had fired since boot (`/proc/interrupts` irq 217 = 0), so the
   card simply looked "not recognised".

Reads are fine at 96 MHz (blkid + fsck read ~16 MB of FAT without error). Only writes fail.

## Proof that it is a bus-speed problem, not the filesystem or the card's data

Runtime experiment (no partition written):
```
# re-probe the host (clears block_bad_card)
printf externdevice | dd of=/sys/bus/platform/drivers/mtk-msdc/unbind
printf externdevice | dd of=/sys/bus/platform/drivers/mtk-msdc/bind
# within ~50 ms of /sys/block/mmcblk0 appearing, before vold's first write:
echo 50000000 > /sys/kernel/debug/mmc0/clock          # -> actual 47999984 Hz, timing still SDR104
echo on > /sys/bus/mmc/devices/mmc0:b368/power/control # stop runtime-PM re-init (MMC_CAP_AGGRESSIVE_PM resets the clock to 100 MHz)
```
Results at 48 MHz: vold mount OK, LOST.DIR created; **16 MiB and 128 MiB random files written and read back,
md5 identical, 0 CRC events, 0 retunes**; ~19 MB/s write, ~18 MB/s read (bus limit at 48 MHz × 4 bit).
Without the clock cap the same write at 96 MHz reproduces the CRC storm and removal every time
(3 of 3 attempts). Runtime-PM (aggressive PM) re-initialises the card at 100 MHz, so the cap is lost on the
first runtime suspend unless `power/control=on`; system suspend (sleep) also re-initialises → the runtime
workaround only lasts until the tablet sleeps or reboots.

Formatting the card is **not needed** (the FAT32 layout is valid and 128 GB FAT32 is fine for Android).

## Card identity
`name=SDABC manfid=0x6f oemid=0x0303 date=09/2024 hwrev=1 fwrev=0 serial=0xaa000610`, 244,306,944 sectors
(116 GiB), `preferred_erase_size=4 MiB`. No well-known brand ID → generic card; its SDR104 write-path margin on
this slot is poor. Whether a brand-name UHS-I card would survive 96 MHz on this slot is untested (the slot's
write-data path is not tuned by MTK autok; only CMD and read-data phases are, and the CMD window is narrow:
`[map:f8000000] [maxlen:5]`).

## Permanent fix (proposed WRITE 6 — needs owner approval, partition write)

Patch the DTB inside the live Magisk boot_b: `mmc@11240000/max-frequency` 100 000 000 → 50 000 000.
Only the SD host is affected (mmc@11230000 is the unused eMMC node; storage is UFS). The kernel then selects
SDR104 at 48 MHz for this card — exactly the configuration verified above — and 48 MHz for any other card.

* DTB location: boot header v2, dtb section at 0x1952800 (size field 186186), FDT magic at +0x40, property value
  at FDT+0x6d3c → **boot_b + 0x195957c**. The dtbo partition does not touch the mmc node (checked).
* Files (`work/sdcard/`, `SHA256SUMS`):
  * `boot_b_backup_magisk_2026-10-18.bin` = live boot_b read via adb 21:47 (sha `170538a9…`, = WRITE 4 image)
  * `boot_b_magisk_sd50mhz.bin` = same image with 4 bytes changed (sha `57d07a2b…`), `cmp -l` shows exactly
    offsets 26580349–26580352 (= 0x195957c–0x195957f): `05 f5 e1 00` → `02 fa f0 80`.
* Script: `tools/scripts/flash-sd50.sh check|write|rollback|reset` (same mtkclient DA path as flash-gsi.sh:
  pre-read assertion that live boot_b == backup, write, exact readback; rollback writes the backup back).
* After boot verify: `xxd -p /proc/device-tree/mmc@11240000/max-frequency` = `02faf080`,
  `cat /sys/kernel/debug/mmc0/ios` shows 47999984 Hz, card mounts, a file copy survives, no `bad_sd` in dmesg.
* Cost: a good SDR104 card would also be limited to ~20 MB/s instead of ~45 MB/s. Fine for an e-reader.
* Alternative worth a later experiment (another boot_b write): drop `sd-uhs-sdr104` + `sd-uhs-sdr50` from the
  node so cards fall back to DDR50 (48 MHz clock, double data rate, ~35–40 MB/s) — untested on this host.

## SD guard across ROM switches (2026-10-18 22:00–22:20)
Owner asked for Magisk + the fix in the stock boot, guarded so it survives switching ROMs.
* The live image already is exactly that: vs the official boot_b the kernel, header, cmdline and os_version are
  identical, the DTB differs only in the 4 cap bytes, the ramdisk is Magisk 30.7 (KEEPVERITY=true,
  KEEPFORCEENCRYPT=true, PREINITDEVICE=sdc14 = `metadata`, SHA1 = official stock 566c9a01…). Nothing in it is
  GSI-specific: the stock ROM uses the same kernel, GPT and partitions.
* Guard implementation and wiring: see docs/STATUS.md (microSD section). Shared logic in `phasec_check.py`
  (FDT walker finds `mmc@11240000/max-frequency` in every FDT of an image).
* Magisk behaviour checked in its scripts (v30.7): a re-patch of a Magisk image restores only the ramdisk and keeps
  the DTB (`magiskboot dtb patch` only edits fstab verity flags; "Failed to patch" = untouched); verified by running
  boot_patch.sh on both the capped plain image and the live image. `restore_imgs` / uninstaller flash
  `/data/magisk_backup_<SHA1>/boot.img.gz` with no hash check → slot filled with the capped plain image.
* Noticed while reading Magisk: its "Install to inactive slot (after OTA)" runs `bootctl set-active-boot-slot` to the
  other slot = slot A here, which is not bootable (banned `set_active a`). Never use that Magisk option on this device.
* The backup slot was briefly created world-writable (0777/0666, adb shell umask) for about a minute; corrected to
  root 0700/0600 with the system_data_file label, and the script now sets it.
